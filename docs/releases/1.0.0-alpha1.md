# pgwrh 1.0.0-alpha1

pgwrh distributes PostgreSQL partition leaves across logical replicas for read
scaling. This release packages four extensions together as version 1.0.0-alpha1. The
[component overview](https://github.com/mkleczek/pgwrh/blob/v1.0.0-alpha1/README.md#components) explains their roles; [cluster
concepts](https://github.com/mkleczek/pgwrh/blob/v1.0.0-alpha1/docs/overview.md) introduces placement and rollouts.

This first alpha is for field testing, not production use. We want feedback on
installation, real query workloads and day-to-day cluster operations before
committing to 1.0.0. Use disposable data or a workload you can recover from
backup. APIs and configuration may change during the alpha series.

## Included in this release

- Versioned shard placement using weighted rendezvous hashing, availability-zone
  affinities and minimum copy counts after a single-zone failure.
- Rollout readiness checks and rollback, with local copies retained while remote
  replacements become ready. Remote subtree aggregation lets a replica query a complete remote partition
  subtree as a unit.
- The bundled `pgwrh_fdw`, with virtual foreign servers, transaction settings
  propagation and replica routing. Stock `postgres_fdw` is not required.
- The independent `pgwrh_wait` extension, which waits for replication through a
  specified LSN before a read takes its snapshot.
- Individual replica credentials with separately salted destination SCRAM verifiers and
  [credential rotation](https://github.com/mkleczek/pgwrh/blob/v1.0.0-alpha1/docs/credentials.md) independent of FLIP/FLOP rollouts.
- The controller-only `pgwrh_ui`: placement previews, replica management and
  rollout diagnostics, served by a separate PostgREST service.
- A Compose quickstart, controller backup and recovery guidance, native packages,
  containers and Nix integration.

## Deployment and limits

Install `pgwrh` with `pg_background` 1.6 or newer. Preload `pgwrh_wait` and
restart PostgreSQL before enabling the wait API. Enable `pgwrh_ui` only in the
controller database; PostgREST is a separate process. The packaged viewer and
operator role scripts grant different levels of access. Put an operator console
behind authentication and HTTPS; the local demo exposes only the viewer on a
loopback address.

Managed replica-to-replica connections require SCRAM authentication. Configure
destination `pg_hba.conf` rules accordingly. Schedule credential rotation
explicitly; topology rollouts no longer change passwords.

The cluster scales reads. Writes go to the controller; it is not a distributed
write coordinator. Logical replication is asynchronous; use the documented wait
API where a read must observe a known write. Placement redundancy does not
replace controller backups or PostgreSQL high availability.

Schema changes require operator coordination. There is no coordinated
schema-change rollout facility in 1.0.0-alpha1. Replica state reports and readiness
checks do not provide a time-based heartbeat or automatic controller election. A
logical controller restore does not restore replication slots or prove existing
replicas safe to reuse; follow the recovery procedure and rebuild replicas as
needed.

There is no cluster-wide replica kill switch yet. If a replica is compromised,
an operator must isolate it and follow the [credential compromise
procedure](https://github.com/mkleczek/pgwrh/blob/v1.0.0-alpha1/docs/credentials.md#compromise-and-recovery). Credential
rotation alone is not a complete incident response. This remains work for
stable 1.0.0.

Only fresh installations are supported. All four extensions share
`1.0.0-alpha1`; migration scripts for earlier development versions are not
included. An in-place upgrade from this alpha to a later alpha or stable 1.0.0
is not promised; plan to recreate test clusters from the controller data.

## Try it and report feedback

Start with the [Compose quickstart](https://github.com/mkleczek/pgwrh/blob/v1.0.0-alpha1/README.md#quickstart), or install the
[native release assets](https://github.com/mkleczek/pgwrh/blob/v1.0.0-alpha1/docs/packages.md). Alpha packages use `1.0.0~alpha1` in
DEB/RPM metadata so they sort before final `1.0.0`; PostgreSQL reports
`1.0.0-alpha1`. Alpha publication does not update the stable APT/YUM repository.

Useful field tests include:

- Installation and console setup on your operating system and CPU architecture.
- Comparing query results and performance with the controller, including reads
  that wait for a known write using `pgwrh_wait`.
- Adding replicas, changing placement and rolling back while queries continue.
- Credential rotation, replica outages, and backup/restore exercises.

Report results and problems through [GitHub
issues](https://github.com/mkleczek/pgwrh/issues), using the field-test template.
Include the pgwrh and PostgreSQL versions, operating system, architecture,
installation method, cluster layout, reproduction steps and expected versus
observed results. Remove passwords, connection strings containing credentials,
and sensitive user data from logs and examples.
