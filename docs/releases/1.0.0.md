# pgwrh 1.0.0

pgwrh distributes PostgreSQL partition leaves across logical replicas for read
scaling. This release packages the controller, foreign data wrapper, replication
visibility barriers and optional browser console together as version 1.0.0.

## Included in this release

- Versioned shard placement using weighted rendezvous hashing, availability-zone
  affinities and minimum copy counts after a single-zone failure.
- Rollout readiness checks and rollback, with local copies retained while remote
  replacements become ready. Remote subtree aggregation reduces routing objects.
- The bundled `pgwrh_fdw`, with virtual foreign servers, transaction settings
  propagation and replica routing. Stock `postgres_fdw` is not required.
- The independent `pgwrh_wait` extension for replication visibility barriers.
- The controller-only `pgwrh_ui`: placement previews, replica management and
  rollout diagnostics, served by external PostgREST with bundled htmx assets.
  Building the UI needs a shell and SHA-384 utility; Python is used for tests.
- A checked Compose quickstart, controller backup/restore regression coverage,
  a recovery guide, native packages, containers and Nix integration.

| Container | PostgreSQL 18, linux/amd64 and linux/arm64 |
| Nix | Linux and macOS, x86_64 and aarch64 |

Every release build must pass installed-package tests, the Compose quickstart,
all core/wait/UI tests including HTTP tests, FDW regressions and TAP tests, and
the signed repository smoke test. This is the required matrix, not a claim that
an unpublished release has already passed it. See the Actions run for its tag.

## Deployment and limits

Install `pgwrh` with `pg_background`'s cookie-protected v2 API (1.6 or newer).
Preload `pgwrh_wait` and restart PostgreSQL before enabling the wait API. Enable
`pgwrh_ui` only in the controller database; PostgREST is a separate process.
The packaged viewer and operator role scripts grant different levels of access.
Put an operator console behind authentication and HTTPS; the local demo exposes
only the viewer on a loopback address.

The cluster scales reads. Writes go to the controller; it is not a distributed
write coordinator. Logical replication is asynchronous; use the documented wait
API where a read must observe a known write. Placement redundancy does not
replace controller backups or PostgreSQL high availability.

Schema changes require operator coordination. There is no coordinated DDL
rollout facility in 1.0.0. Replica state reports and readiness checks do not
provide a time-based heartbeat or automatic controller election. A logical
controller restore does not restore replication slots or prove existing replicas
safe to reuse; follow the recovery procedure and rebuild replicas as needed.

The existing installation policy remains fresh installation only. All four
extensions share 1.0.0; migration scripts for earlier development versions are
not included.
